# 淘宝归类 v2 扩大覆盖：出售中商品支持 — 设计文档

日期：2026-09-24
状态：已确认（用户批准方案 A）

## 背景与问题

用户观察到「出售中商品分类丢了很多」。排查结论（见 2026-09-24 诊断）：

- **分类没有丢失**。所有被归类任务成功处理过的商品（done 866）分类完好：
  - done∩仓库中 抽样 10/10 有分类；
  - done∩出售中 抽样 15/15 有分类。
- 出售中列表（实测采集 2253 个）约 90% **从未进过归类计划**（穿戴甲新品线等，创建于 08-27 前后就一直在售），不是丢失而是从未覆盖。
- 旧 plan 只覆盖 2026-09-13 采集的仓库中 1942 个商品：done 866 / failed 832 / 未处理 440。
- failed 832 拆解：513 数据问题（表单校验拦提交，需人工修数据）、202 复核分类空（提交未生效，可重试）、65 页面加载失败（可重试）、41 分类未改判成功（旧分类还在，可重试）、其余零星。
- 现有 v2 流程 `check_listing_mode` 硬性要求上架时间=放入仓库，**出售中商品会被直接 fail**，因此从未覆盖在售池。

## 目标

1. 归类覆盖扩大到出售中商品，编辑提交后保持出售中。
2. 清完仓库池剩余（440）。
3. 重试可修复的 failed（202 空分类 + 65 加载失败 + 41 未改判 ≈ 308）；513 数据问题不自动重试（需人工修数据，重试永远失败）。

## 用户已确认的决策

| 决策点 | 结论 |
|---|---|
| 范围 | 三块全做：出售中 ~2000 + 仓库剩余 440 + failed 重试 |
| 在售编辑副作用 | 保持出售中；调价（货源价+130）与删横版视频实时生效 |
| 顺序 | 出售中优先 → 仓库剩余 → failed 重试 |
| 实现 | 方案 A：扩展现有 v2（不复制 v3） |
| 调价范围 | 仍只限「家居服/睡衣」「美甲」（2026-09 用户指令，其他类目勿动价） |

## 设计

### 1. 数据管道

**`collect_in_stock_current.py`** 加 `--list in_stock|sold_out` 参数（默认 in_stock 保持兼容）：

- `sold_out` 采集 `https://myseller.taobao.com/home.htm/SellManage/sold_out?current=1&pageSize=20`（翻页必须点「下一页」，goto 改 current 无效——既有经验）。
- 输出新文件 `taobao_onsale_current.jsonl`（不动现有 `taobao_in_stock_current.jsonl`）。
- 复用现有断点续跑、去重、弹窗处理逻辑。

**`build_shop_cat_plan.py`** 加 `--merge` 模式：

- 旧 plan 1942 条的 `category` 判定**原样保留**（done 866 的复核依赖它，绝不能按新规则重判）。
- 新商品 = (在售池 ∪ 仓库池) − 旧 plan 已有 itemId，走现有 `classify()` 八类目规则（美甲→牛仔短裤→秋冬款→半身裙→连衣裙→长裤→家居服/睡衣→other）。
- plan 条目增加 `pool` 字段：`onsale` / `warehouse`（按商品当前所在列表标记）。
- 输出仍为 `shop_cat_plan.json`（结构向后兼容：多一个字段）。

**进度文件**沿用 `shop_cat_v2_progress.json`，done/failed/skipped 按 itemId 跳过，与 pool 无关。

### 2. v2 状态自适应（核心代码改动，集中一处）

`assign_shop_category.py` 的 `check_listing_mode`（v2 引用）由「必须=放入仓库」改为**读当前选中状态并原样维持**：

- 「放入仓库」→ 返回 ok（仓库商品，维持下架待上架态）。
- 在售态（radio 显示「立刻上架」）→ 返回 ok，**不点击任何 radio**，提交即保持出售中。
- 其他值 / 找不到字段 → 仍 fail（异常状态宁可不做）。

`assign_shop_category_v2.py` 的 `process_one` 相应调整：不再因「上架时间非放入仓库」拒绝在售商品；其余流程（调价、删横版视频、弹框处理、verify_by_reload、二次提交）全部不动。

- 无货源价（DB 查不到绑定）→ 只归类不调价，进 `noprice`（现逻辑已支持）。
- 删横版视频对在售商品实时生效（用户已确认）。

### 3. 执行顺序与重试策略

1. plan 排序：`onsale` 未处理优先 → `warehouse` 未处理 → failed 重试队列追加尾部。
2. 重试队列 = failed 中「空分类 202 + 加载失败 65 + 未改判 41」≈ 308 个；513 数据问题保留 failed 不动。
3. **探路**：在售路径全新，先 `--limit 3` 验证三件事：提交后仍在售、分类正确写入、调价按规则生效。确认后再放量。
4. 量级预估：~2960 个 × 60-80s ≈ 50-65 小时（多天，含风控冷却另加）。窗口模式 Chrome（9222），`run_cat_v2.sh` 自愈循环（exit 42 → 降级跑货源销量 → 阶梯冷却 20m→40m→2h 封顶）沿用。

### 4. 风险与运维

| 风险 | 处置 |
|---|---|
| 在售批量编辑触发风控 | 阶梯冷却自愈沿用；探路阶段重点观察 RGV587 出现频率，异常则降速/暂停 |
| cron 冲突（05:00/06:00 用 9222） | `inventory_cron.sh` 已有「归类v2运行中→跳过」守卫，无新工作 |
| 双实例 | `run_cat_v2.sh` shlock 锁已有 |
| 提交半途失败 | 既有安全网：分类设置失败不提交；提交失败即未保存，无副作用 |
| 日志丢失（上次 cat_v2_run.log 被清） | 本次运行期间不动日志文件；结束后归档 |

## 不做的事（YAGNI）

- 不新建 v3 脚本。
- 不改八类目规则和调价规则。
- 不自动重试 513 数据问题（人工修数据后可手工触发 `--retry-failed`）。
- 不处理 草稿(467)/回收站/违规 池。

## 验收标准

1. 探路 3 个在售商品：编辑提交后仍「出售中」、店铺分类=plan 判定、价格符合货源价+130（有货源价时）。
2. 出售中未归类商品跑完后，抽查 20 个：分类正确率 ≥95%。
3. done 商品零回归：任一 done 商品分类不变（进度按 itemId 跳过保证）。
